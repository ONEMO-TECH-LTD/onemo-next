## 1 · What the pipeline is, and what we intended with it

**In one line:** shape in → know what it is → know where its centre is → look up the layouts its class
carries → wrap each one exactly → offer every lawful result, neutral.

**The intent** (from `v3.5.6-current-brief.md` §1 and §7): one calibratable, **neutral** engine that
automatically finds the layouts Dan can already produce by hand with the same controls — returning
*every* distinct lawful result with its evidence, hiding nothing because another result has a higher
count, appeared first, or scored better, and never reporting "no fit" while a lawful arrangement exists.

**Why a pipeline at all, rather than a search.** Dan's rejection of the alternative is explicit:

> *"why do we need to search for all 1m arrangements ? who designed that? we need to find arrangenments
> that filter through 3 laws"*
>
> *"compute must compute in the bounds of the task and procedure we set it is simple as that it doesnt
> tneed to compute all possible arrangements first"*

So each step **bounds** the next. Class bounds the layouts. Layout bounds the size. The wrap seals it.
Nothing generates a universe and filters afterwards.

**What is invariant across every step** (locked 08-24 14:34, *"yes only rigid rules are grid is static
and objects only appear in set seats and shape can only deform when we allow otherwise it is only
proportionally scaling"*):

1. **The 48mm lattice is rigid** — never rotates, never deforms, never re-registers per candidate.
2. **Magnets exist only at lattice seats.**
3. **The shape scales proportionally.** Deformation is an explicit permission, never a default.
4. **12mm padding is built into the magnet** (Dan, 08-26 14:25: *"it is built into the magnet so whatever
   shape is it is padded by that guaranteed inset"*; *"8mm is 12mm now"*). One constant, one home.
5. **Scale is the search action, not a law** (the standing three-law brief).

## 2 · The steps

### STEP 1 — Segmentation · 12mm erosion · legal area · CLASS

*Once per shape, at load, size-free in identity. Scale never changes what the shape **is**.*

**Contains**

1. Erode the traced outline by 12mm → the **legal area**: where a magnet centre may sit.
2. Measure it — islands, their masses, deep points, and the **segment box**.
3. Read the **class** off the segments — family, kind, and the frame per band.
4. Show it in the admin panel, by name, for validation by eye.

**The 12mm rim is physical and does not scale**, so the *legal area* genuinely differs at each size (a
100mm square's legal box is 76mm, not a scaled 88); only the **outline's own features** (centre,
silhouette, family) are scale-free. **Settled:** the legal area is measured at the current size — that is
universal eligibility, not a per-shape choice. **Open — OQ1:** family read from the silhouette while
frame and kind come from the current legal-area segments, or everything from the segments?

**Where this stands in code:** `grid-lab-architecture.md` §3–§4. *(The old step-1 unit sheet is archived:
it marked `shapeFamilyOf` and the classifier panel "done" against the three-family target both documents
now delete.)*

### STEP 2 — CENTRE, named by the class

**Contains**

1. The class points at its **pre-decided centring mode** (Dan, 17:02). *The class → centring-mode table
   is still Dan's to rule — it is deliberately unfilled.*
2. Fix the centre spot **once per shape**, then scale it linearly with the shape.

**Why once.** Dan, 08-25 13:56: *"we just need to measure the center once and stick to it maybe this is
why bot with pair is also lopsided"* — and it was. The centre is a property of the shape, not of the
size; re-measuring it per size on the 2mm mesh produced 2mm jitter and 30mm governing-mass flips, and the
wobble was what made the BOT's pair lopsided. Fixed 08-25 14:01: worst grid movement per step went from
2mm pops + 20–36mm leaps to 0.69mm smooth, and the centred pair appeared by itself.

**What legitimately changes with size:** not the candidate points — only which of them **qualify**,
because the 12mm clearance is fixed while the shape scales. Positions never move; qualification does.

**Group centre vs shape centre** (Dan, 08-25 14:02):

> *"the moving center can be only the group center when we allow it to didviate from the center of the
> shape - the shape center must match with group center only when wrap applies and we optimise the wrap
> - we can evaluate group center shift from the shape center shift - but this must be an exception and
> part of the fine tune"*

And the four centring rules that govern that exception (Dan, 08-24 19:26 / 19:47):

> 1. Put the group centre on the shape centroid.
> 2. Shrink/wrap from that centred position.
> 3. Shift only by the **minimum** amount necessary to obtain a lawful tighter wrap.
> 4. Prefer the tight solution **closest to the centroid** — not the smallest shape at any centering cost.
>
> *"centroid guides selection; it never forces enlargement or overrides contact"* (19:26).

**Derived-centre proposal (Dan, 08-25 16:58, agreed in principle, not ruled):** define the centring from
the legal area itself — one mass → that mass's own centre; several masses → the **governed top mass**
(gravity first). A mass centre is by definition inside seatable material, so the void-anchor failure
(Box/Core/Weight landing in the duck's neck) becomes structurally impossible.

### STEP 3 — LAYOUT, from the library

**This is where the shape library belongs.** The class does not invent an arrangement; it **looks one up**.

**Contains**

1. The recognised class + the band's frame → the **catalogue's layouts for that class**.
2. Each layout is a disk arrangement on the rigid lattice, with its populations —
   `full · perimeter · corners`, perimeter carrying the spacing mode `48 · 96 · custom`.
3. The reveal scan (seat everything the material offers at a size) survives only as a **fallback** for
   when no catalogue entry holds.

**The ruling that made this the design** (Dan, 08-25 15:39, on whether a measured anti-flap judge should
rank layouts): the **class itself is the guard** — a correct catalogue makes a flapped layout impossible
to offer, rather than detected afterwards. *(Provenance: the collector kept only the screenshot half of
that Dan turn; the ruling survives as the quoted phrase "the class itself must be it" inside the lead's
same-turn reply, uncontested. The line below is verbatim from Dan's turn at 15:39:40.)* The Clipper
subtraction stays only as the **repair**:

> *"but if not enough use your clipper 2 fix that substracts and elipses show unprotected edge perimeter
> and forced to place magnet there with relevant wrap and layout"*

**What the library is** (Dan, 08-26 14:01 and 14:04):

> *"we dont care about the shapes this ios library of the disk layouts - outlines are for illustration
> and categorisation ease"*
>
> *"if we decide to release the shapes as presets to product we must have them stored - store layouts and
> shapes in the catalogue"*

So: **the disks are the product**; the outline is illustration *and* the categorisation handle; and every
entry is frozen as a **layout-and-outline pair** so a shipped preset stays put while the generator stays
live. Entry identity = **layout + outline in orientation** — never the layout alone (Dan, 08-26 15:39:
a 1×1 square and a 1×1 diamond are different products because the print's relation to the shape differs).

**The class taxonomy, as ruled — both layers**

*Primitive families* (Dan, 08-24 23:26):

> *"rectangle and square are just basic shapes made of square - circles and ovals are rounded versions of
> them - triangle and diamond are similar and Tand L shapes are all tringle group"*

→ **SQUARE** (fills its frame) · **ROUND** (same counts, sizes grown by corner padding) · **TRIANGLE**
(partial frame only — apex, corners, chains, diagonals; never the full field).

*Product classes in the library* (ruled 08-25 evening, and these supersede the family list **as the
library's class list**, not as the grouping):

- *"Square is square class period rectangle is rectangle class"* (18:44) — split apart.
- Diamond is its own class (18:42) — because its ring runs at **45° to the lattice**, a genuinely
  different node geometry. *"No rotated square, rotated square is not on the lattice. Lattice does not
  rotate."*
- Classes must be **pure** (18:50): *"Diagonal 2 magnets are not square it is diamond. You joking you
  really don't understand why we need different Classses to be pure?"* A class that admits foreign
  patterns cannot decide anything.
- **Round is not a separate class** (23:36): *"round is square and diamond fit so it is not real
  different the bbox is square"* — a circle takes square and diamond patterns; round-ness is a **corners
  qualifier** (`round | sharp | bevel`) on the one producer, not a taxonomy.
- Triangle is a class (mirror-symmetric about one axis only), built on the square/rectangle frames.

*Class shape* (Dan, 08-24 23:20 / 23:24): class = the **axis pair `cx × cy`**, band = the larger axis
class, **slim = minor 1–2, standard = minor 3–4**, square = `cx = cy`. Capacity = `cx · cy`, reduced by
the perimeter rule.

*Runs* (Dan, 08-25 14:50 and 23:52): thickness comes from width — under 48mm = one line, 48–96 = two,
each further 48mm adds one. A run either **holds its thickness** (rectangle), **tapers to a point**
(triangle/cone), or **meets another run** (an L at a corner, a T at a midpoint — two runs joined, not a
pattern of their own).

### STEP 4 — WRAP seals it, last

**Contains** the Clipper2 exact solve, unchanged since Dan accepted it on 08-24 17:11
(*"ok the wrapping works now congratulations"*):

1. Deflate the outline by the padding → exactly where a magnet centre may legally sit.
2. Translate that region by each magnet's offset and **intersect** → every grid position where the whole
   rigid group is seated. Non-empty ⟺ it fits.
3. **Binary-search the size** for the smallest that still fits — exact to 0.01mm.

The group **starts** on the centre and shifts only the minimum a lawful tighter wrap demands — the
cove-dip of Dan's own contract line. It cannot stop early or jitter, because the fit test is a boolean
and the size is solved, not crept toward.

**The model this implements** (Dan, 08-24 14:30): omnidirectional gravity — *"the shape wraps around it
and grows and wraps around it with every object addition."* For any magnet set there is exactly **one**
tight size.

**Band membership** (Dan, 08-24 18:27): a layout whose **true** wrapped size falls outside a band **does
not exist in that band**. No clamping to band floors.

### STEP 5 — JUDGE and OFFER

**Contains**, in fixed order:

1. **The 96mm perimeter law** (Dan, 08-25 10:03):
   > *"unheld are between extreme perimeter is fine edges unprotected is bad every minimum 96mm of
   > perimeter must be pinned"*

   It is an **arc** measure along the outline, never an area. Ranking by unheld *area* is dead — it ranked
   Dan's correct 143mm duck **below** the wrong 125mm one. Exception: **1–2 magnets** are judged by
   centring/balance, not perimeter (Dan, 10:16).
2. **Gravity first** (10:08): *"gravity rule still stands top flap is priority always."* The upper mass is
   pinned before anything below. A single magnet in the middle of a mass pins nothing — a **pair across
   the width** breaks the run.
3. **Segment-edge priority** (10:16): *"prioritise segment edges and not leave any segment or edge
   unprotected"* — with the shape scaled to make the needed seat exist.
4. **Coverage dominance** — at the same size, the layout holding more wins.
5. **Best class match** — a native catalogue layout outranks a repaired one, which outranks a discovery.
6. **Landing** — fewest magnets that satisfy everything, then least shift. Every other lawful result
   stays offered; nothing is deleted to make the answer look tidy.

**Two hard constraints on this step**

- **Count is exact — no silent drop in the solver** (10:00): *"it must not be silent drop it must be exact
  number set just different layout and seat filled."* The frame and the size move to deliver N; the
  interior is never populated to make up the number.
- **Perimeter is the manufacturing default** (09:57): *"it is correct behavior w dont need gilling center
  magnets we need to pin perimeter along the edges - simple."* The perimeter belt's subtractive
  count-drop is **correct behaviour**; that is not in conflict with the line above.
- **More magnets ≠ a bigger shape** (08-24 22:18) — offer the next rung, not a 100mm leap.

## 3 · THE SHAPE CLASSIFIER — what it was meant to deliver

**Its role in one sentence: the classifier BOUNDS THE SEARCH.** It converts a shape into *which layouts,
which counts, which sizes to try*, so the engine tries real buildable arrangements instead of generating
everything. That is the answer to Dan's *"why do we need to search for all 1m arrangements?"*

**Dan's own statement of the deliverable** (08-25 10:25):

> *"we classified shapes based on geometric shapes like square and rectangle etc - each actually has
> matching magnet coun x size (if not perimeter applied it is standard) so we can recount with the
> perimeter and understand what the bands are actually and what layout and number of magnets and sizes
> range is expected from classified shape."*

**→ classified shape → expected layout × count × size range, recounted with the perimeter rule.**

### What it must deliver

1. **The class of the shape** — read from the segments/legal area: family, the axis pair `cx × cy`,
   kind (slim / standard / square), and the frame per band.
2. **The candidate set that class implies** — the expected layouts, their counts and their size ranges.
   Dan, 08-28 07:59: *"we need classifier to recognise that matching shape is triangle rectangle diamond
   or square - the specifics like T and L is just same basic canon classes with some disck taken out"*
   (and *"Rectangle is H with mid taken out"*).
3. **Answers drawn FROM THE CATALOGUE, not from a hardcoded list.** Dan, 08-26 13:46: *"we need to build
   library in such a way that output catalogue is clean and can be fed in the standard format into the
   engine classifier."* Dan, 08-28 09:30: *"it was always the plan for classifier to answer from the
   catalogue."*
4. **Adaptable and expandable, automatically.** Dan, 08-28 09:27:
   > *"the library is always work in progress the classifier needs to be adaptable and expandable to
   > scale automatically not be hardcoded it scans catalogue of the library"*

   Add a shape to the library → it is in the candidate set. **No classifier edit, no plan rewrite.**
5. **A visible decision trace.** Same turn: *"we must be able to see each time when shape classified how
   it made the decision as verifier visually as well."* For any shape: the candidates considered, what
   discriminated them, why it landed where it did — on the surface, not in a log.
6. **A standing audit inside it.** Same turn: *"audit test inside it so we have no silent
   miss-classifications."* Every catalogue record must classify to its own class, and **ambiguity must be
   reported, never silently resolved.**

### What it is NOT

- **Not a lookup table replacing generation.** The solver already seats magnets in *any* region
  (`latticeOver` + seat predicate + `splitPerimeter`) — unknown shapes are handled by generation. Dan,
  08-28 08:01: *"we can make classifier automatic for any shape - beyond L and H there could be others we
  do not know about and basic shapes must automatically adapt to them."* Enumerating every possible shape
  is a race that cannot be finished.
- **Not a hardcoded family enum with tuned thresholds.** `shapeFamilyOf`'s `fill < 0.68` cut and its
  `0.08` / `minor <= 2` constants are salvaged, exemplar-tuned numbers with no ruling behind them.
- **Not a coarse pre-filter that can discard the right answer.** Today the hardcoded family gates the
  catalogue match — a wrong family silently removes the correct entry before anything else runs. The
  dependency runs backwards and must be inverted: the catalogue defines the classes; the classifier reads
  them.

### Measured state (08-28, my probes)

| | |
|---|---|
| Library class → what `classifyShape` answers | square (16) → `square` · rectangle (38) → `square` · diamond (13) → `triangle` · triangle (96) → `triangle` |
| Answering from the catalogue on the current coarse key | **123 of 163 decided · 40 ambiguous · 0 missed** — the baseline *before* the Pareto classifier, not the proposed result |
| Matcher key today | `(family, cx, cy)` — average **9.5** candidates returned, 16 for diamonds |
| `round` family | reachable by nothing in the library; a pill classifies as `square` |
| Engine consumption | **none** — `solve.worker` does not consume the catalogue matcher |

The catalogue path **never misses**; it is only sometimes undecided, and the 40 ambiguous cases are
exactly those where the key ignores the fill, aspect and frame it already computes. The hardcoded path
can *never* separate square from rectangle, or diamond from triangle.

The **proposed** classifier — exact axis-pair filter, then a Pareto frontier over fill and aspect error —
and its measured result at all three pitches live in `grid-lab-architecture.md` §4. This section is what
the code answers **today**.

**One genuine defect, open:** 4 of 38 rectangle records report `cx = cy` — a rectangle carrying a square's
axis pair. That is a silent misclassification of the kind the standing audit exists to catch.

**Honesty boundary, standing:** *the catalogue is not "fed into the engine" until the solver consumes the
matcher.* Until then the status is **"contract landed, runtime consumption pending"** — never
"integrated".

## 4 · The library's place in the pipeline

**The expected layouts and counts the classifier hands the search ARE the catalogue.** The classifier does
not own a list of shapes; it reads the shape, and the catalogue supplies the candidate arrangements for
it. **Library grows → search space grows → no classifier edit.**

The catalogue has a **second job** the generator cannot do for itself: it is the **certified set** — the
163 frozen records at 24/48/96mm are the cases where the right answer is known, mm-exact. A generator
with nothing to check against is guesswork with extra steps. (This is what the solver-vs-catalogue oracle
now asserts; it found the y-flip registration defect — 68 records / 204 pitch-cases — on its first run.)

Format: one record per entry — class, type, stable id, disk positions in mm, outline polygon in mm, size —
every class through the same producer, the outline computed from the disk layout and the built-in 12mm
padding so nothing is hardcoded.
