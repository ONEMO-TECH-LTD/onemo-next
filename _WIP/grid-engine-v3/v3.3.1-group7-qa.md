## Verdict

## Blocker — benchmark substitutes a final-result cache hit for computation

`scripts/benchmark.mjs:25–35` clears the caches once, solves one outline, then repeatedly submits that identical outline and profile. `packages/magnetic-logic/src/solver.ts:36–42` returns the cached final `SolveResult` before `solveSizeSequence` runs. The test also asserts repeated solves return the same object. The recorded approximately 0.55 ms therefore measures profile validation, hashing and map lookup; no rung is re-certified during a timed sample.

Independent exact-commit probes separated the two operations:

- identical final-result cache hit: **0.319 ms**, same object identity, with 21 previously stored rung results;
- actual warm 21-rung computation from one already-prepared source: **44.50 ms median, 45.04 ms p95, 46.95 ms max** over 30 samples after 20 warm-ups;
- 20 unique warm cache-miss solves: **45.14 ms median, 46.64 ms p95, 46.99 ms max**.

The implementation is below the >50 ms hard-rejection boundary on this stabilized probe, but it does not meet the ≤16 ms target in `00-system-contract.md:532–539`. The submitted PASS also conflicts with the benchmark contract:

- the Compute contract's permitted-cache list names prepared geometry, measurements, safe regions and component hierarchies, not final `SolveResult` objects (`01-compute-engine-spec.md:604–620`);
- Logic permits excluding cached profile resolution/hashing when disclosed, not the entire computed answer (`02-logic-engine-spec.md:1106–1114`);
- one 12-edge outline is used instead of a representative corpus, and the report omits browser version, radii, pattern-point and size/registration counts, plus memory evidence required by `01-compute-engine-spec.md:835–850`. R3 names the approved backend-probe corpus in §9.3, but it does not identify a separate approved “typical all-band” artifact; Batwoman remains explicitly unavailable.
