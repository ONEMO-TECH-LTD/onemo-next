## 1 — 2D physics engines (soft-body / cloth wrapping)

From the document's first answer, before the rigid-lattice constraint was stated.

| Engine | Link | What the document says |
|---|---|---|
| **Matter.js** | https://brm.io/matter-js/ | Fast lightweight 2D JS physics. Built for rigid bodies, but composite + constraint systems let you link particles into a grid to make a cloth/wrapping net that drapes over shapes. Later named again for the blob-boundary approach: build the blob from a chain of small circular bodies on tight constraints, then reduce their resting length over time so the loop shrinks around the disks. |
| **QuarkPhysics** | https://github.com/erayzesen/QuarkPhysics | Lightweight 2D open-source library that natively supports rigid bodies **and** soft-body / shape-matching dynamics — so wrapping and deforming around items is built in rather than assembled. |
| **Jolt Physics** | [NO LINK IN DOC] — https://github.com/jrouwe/JoltPhysics *(added)* | Very fast multi-core modern C++ rigid + soft-body engine. The document notes it is "more robust than a tiny script" but highly optimised. |
| **Planck.js** | https://piqnt.com/planck.js/ | JS port of Box2D. Build the blob boundary as a single `b2ChainShape` or bodies joined by `b2DistanceJoint`s; move anchors inward / reduce joint lengths to pack the disks. |
| **Box2D** | https://box2d.org/ | The C++ original behind Planck.js. Same approach. |
| **Pymunk** | https://www.pymunk.org/ | Lightweight Python wrapper over Chipmunk2D. Loop of segment shapes or pin-jointed particles, each pulled toward the disks' centre of mass. |
| **feather** | https://github.com/BarthPaleologue/feather | Cited as reference [1] for the soft-body/cloth claim. The document does not describe it. |

**The document's own caveat on this whole family** (worth reading before testing any of them):
standard engines "can sometimes jitter when constraints are heavily over-compressed", which is
why its own prototype used a hand-written Verlet loop instead. And once the rigid-lattice
constraint was stated, it reversed on them outright: physics engines are "actually a poor fit"
because they treat every disk independently, so the grid "would deform, break apart, or jitter
wildly when crammed into tight coves."

## 2 — Methods, no dependency (the document's "list all solutions")

### 2a · Physics-loop family (dynamic)

| Method | How it works | Document's stated pros / cons |
|---|---|---|
| **Distance joint chain (rope boundary)** | Closed loop of tiny overlapping rigid circles joined by distance joints; decrement every joint's `restLength` a fraction per frame. | Pro: handles complex non-convex blobs. Con: joint jitter or explosion when shrink force overpowers disk collision. |
| **Central gravity inward pull** | Same boundary loop, but instead of changing joint lengths apply a continuous inward force to each particle toward the disks' geometric centre. | Pro: highly stable, self-correcting. Con: snags on protruding disks, so it misses optimal packing in deep pockets. |
| **Pressurized soft body (reverse inflatable)** | Native soft-body engine; set internal pressure negative or continuously drain the hull's "volume". | Pro: smooth organic deformation out of the box. Con: cannot reach true zero-gap precision because of spring-damper tolerances. |
| **Verlet integration loop (custom)** | What the document's own prototype used: 60–100 node closed chain, resting lengths multiplied by ~0.994 per tick, plus point-to-circle projection snapping any penetrating node back onto the disk perimeter. Nodes then slide frictionlessly along disk edges into the concave pockets. | Stated as ~80 lines of clean code, no framework. |

### 2b · Computational geometry family (static — "mathematically perfect tightest fit")

| Method | How it works | Document's stated pros / cons |
|---|---|---|
| **Taut string / convex hull wrapping** | Modified Gift Wrapping (Jarvis March) or Graham Scan adapted to circles instead of points: outer common tangents between adjacent perimeter disks (parallel to the centre-to-centre vector when radii are equal), joined by circular arcs along each disk's edge at `θ = atan2(yB−yA, xB−xA)`. | Pro: instantaneous, absolute zero-gap, mathematically flawless. Con: **convex only** — it bridges across gaps instead of dipping into a concave blob. |
| **Alpha-shape / concave hull ("rolling ball")** | Delaunay triangulation on the disk centres; discard triangles whose edges exceed the rolling radius α; trace the boundary of what remains; offset it inward by the disk radius. On our 48mm lattice: α > 48 bridges the gaps, α < 48 squeezes into the internal channels. | Pro: lets the boundary dip deep between disks. Con: computationally intense, fiddly on overlapping edge cases. |
| **Iterative vertex relaxation (snakes / active contours)** | Fine polygon loop around the disks; each vertex steps inward; any vertex that penetrates a disk is projected back out to exactly the disk radius; stop when no vertex can move. | Pro: no physics engine, no mass/velocity, very light, handles non-convex. Con: needs custom circle–segment intersection maths. |

### 2c · Grid / field family (discrete)

| Method | How it works | Document's stated pros / cons |
|---|---|---|
| **Distance-field shrink-wrapping** | Build a Signed Distance Field of the disks on a fine grid; start the outline far out and march it inward down the field gradient until distance to the nearest disk surface is exactly zero. | Pro: visually flawless, organic, handles topological splitting. Con: higher memory, bound to grid resolution. |

## 3 — Rigid registration / shape matching (for when the grid pans into the coves)

Named after the "the disk grid can pan and move to adapt" turn. These solve *where the rigid
grid sits*, not what size the shape is.

| Method | How it works | Mobile note from the document |
|---|---|---|
| **ICP — Iterative Closest Point, grid-constrained** | Sample control points along the shape's inner valleys; for each, find the nearest lattice disk; least-squares the optimal translation + rotation; transform the whole grid; repeat 5–10 times. | Very fast — because the lattice is uniform, "nearest disk" is `Math.round(x / 48) * 48`, no array search. |
| **Distance-field optimisation ("sinking")** | Bake the shape into an SDF / cove map once; sample the gradient under every disk inside the shape; sum the gradient vectors into ONE global translation + rotation for the whole grid; apply per frame. | Behaves like physics but computes a single global vector per frame instead of hundreds of collisions. |
| **Medial axis alignment** | Compute the shape's topological skeleton; align the lattice's primary axis to the skeleton's dominant angle; snap the grid origin to the deepest vertex of the main cove. | Instant, single frame on load, zero ongoing battery cost. |

The document's own decision rule between them: gradient/SDF if you want the grid to visibly
slide and lock; ICP/least-squares if you want it to snap instantly.

## 4 — Libraries for rigid nesting & matrix transforms

This is the "mobile friendly" list — the section that produced Clipper2.

| Library | Link | What the document says |
|---|---|---|
| **Clipper2** `[IN USE]` | https://github.com/AngusJohnson/Clipper2 | Industry-standard polygon clipping, offsetting, intersecting. Inflate/deflate the shape by exactly the disk radius; the remaining interior shows exactly where the grid's centre points may slide; if the grid tries to pass that boundary Clipper gives the instant intersection vector to snap back to a zero-gap lock. **This is the method now running in Wrap mode** — `@countertype/clipper2-ts` was already a dependency. |
| **SVGNest / DeepNest** (libnest2d JS ports) | https://github.com/Jack000/SVGnest | Geometry engine built for nesting rigid parts into irregular containers with zero gaps. Treats the 48px grid as one compound boundary polygon and the shrinking shape as the container, then uses a **No-Fit Polygon (NFP)** algorithm to compute exactly how to slide and rotate the grid flush into the tightest internal corners. Pure geometry, no physics loop, "a few milliseconds". |
| **Libnest2d** | [NO LINK IN DOC] — https://github.com/tamasmeszaros/libnest2d *(added)* | Header-only C++ library for optimal rigid polygon packing and containment; the engine 3D printers use to arrange models on a print bed. Supply the shrinking shape and the disk cluster; it finds the global X, Y translation and rotation θ that slips the cluster deepest into the container's valleys. Compiles to almost 0KB. |
| **Turf.js** | https://turfjs.org/ | Modular ultra-light computational-geometry library, named twice. Treat the shape as a Polygon and the grid as a MultiPoint; use `booleanContains` / `difference` as the shape scales, and on intersection compute the overlap vector and shift/rotate the whole grid matrix away from that wall, deeper into the coves. Also proposed for finding the coves themselves via concave hulls / vertex analysis, then `transformTranslate` / `transformRotate` on the grid. |
| **OpenCV-Lite / OpenCV Mobile** | https://github.com/nihui/opencv-mobile | Stripped-down OpenCV for Android/iOS, heavy imaging removed, raw geometry modules kept. Use Template Matching or ICP: feed the coves as a point cloud, get back the exact 3×3 transform (x shift, y shift, rotation) to drop the grid into the pockets. Microseconds, C/C++. |
| **Eigen** | https://eigen.tuxfamily.org/ | High-performance C++ linear algebra templates. Run the least-squares that snaps the grid to the cove coordinates — supply cove vectors and grid vectors, get one translation/rotation matrix. |
| **Defold** | https://defold.com/ | Tiny-footprint C++/Lua 2D game engine. Not for its physics: parent every disk sprite under one GameObject and slide/rotate the single parent node, so children can never drift off the 48px spacing. |
| **PixiJS** | https://pixijs.com/ | Named alongside Defold for the same single-parent-transform trick: one collision hull on the shape, correction vector applied to the whole parent node. Mobile GPUs process parent-child matrix hierarchies natively. |
| **Vanilla JS matrix loop** ("RoboFormulas") | [NO LINK IN DOC] | No engine at all: map the shape into a 2D array or canvas bitmask and use `ctx.translate` / `ctx.rotate` with a custom gradient-descent script to find the lowest-energy fit. 0KB footprint. |

## 7 — What this repo already has

Stating it so a test doesn't re-import something we own.

- **Clipper2** — `@countertype/clipper2-ts` in `package.json`; used by `insetRingMM` (outline offset) and by the whole Wrap solver (`grid-magnet-wrap-compute.ts`): deflate by disc radius → intersect the region translated by each magnet offset → binary-search the size.
- **A marching-squares SDF** — `safeSegments` in `grid-magnet-compute.ts` samples signed clearance on a 2mm mesh, finds islands and masses, and traces level crossings with linear interpolation. This is method 2c already built, for centring rather than wrapping.
- **A point-query SDF** — `signedClearanceMM` in `grid-magnet-compute.ts`: signed distance at a point off the bucketed edge index. Currently **unused** since the Clipper rewrite.
- **Exact seat legality** — `makeSeatPredicate` (integer-micron, tangency by equality) and `makeCircleSeatPredicate` (analytic circle).
- **A V2 rigid-lattice nesting port** — built and discarded 2026-08-24: force + cross-product torque on a rigid group. Rotation knocked magnets off the drawn lattice (our board cannot rotate) and the push-back nudge stalled, reading "stuck" as "jammed" and stopping several mm loose. Not a fault in the method; a fault in applying a rotating-group method to a non-rotating board.

## 8 — Non-obvious side value

Where a method's *direct* application isn't our case but something it produces might be.

- **No-Fit Polygon (SVGNest / libnest2d).** Direct nesting isn't our problem — our group is fixed and only the container scales. But the NFP of the magnet group against the shape **is** the set of lawful grid origins, which is exactly what our Clipper intersection computes by hand. An NFP implementation would give the same set with the sliding contact structure attached — i.e. *which wall* is blocking, not just that something is. That is the missing direction information: our wrap measures proximity with no notion of side, which is why an opposing-pair test can't be expressed today.
- **Alpha-shapes / rolling ball.** Not a wrap. But α is precisely "how far can material reach past the last magnet before it hangs loose" — the flap/coverage question, in a parameter with real geometric meaning instead of the mm² threshold that was invented and rejected.
- **Medial axis.** Not a placement rule for us. But the skeleton names a shape's limbs and where they attach, which is the structure the layout qualifier needs to say "the head is a separate limb and nothing holds it".
- **ICP.** We do not rotate. But its cove-anchor sampling — find the sharp inner valleys and treat them as targets — is a candidate-generation method: place magnets *at* the coves instead of taking the N seats nearest the centre. That directly attacks the "only compact clusters are tried" limit.
- **Convex-hull tangent wrapping.** Convex-only, so it cannot wrap our shapes. But the tangent/arc construction gives the exact contact geometry between a disc and a straight wall, which is what a true contact readout (which discs press, on which side) needs.
- **Turf.js.** Overlaps Clipper2 heavily for booleans. Its distinct value is `transformTranslate`/`transformRotate` plus concave-hull utilities — cove-finding — rather than the clipping we already have.
- **Verlet relaxation / active contours.** We rejected iteration because it stalls. But an iterative relaxation is the natural way to answer "where does material actually hang loose", by letting a boundary settle onto the magnet set rather than solving for it.
