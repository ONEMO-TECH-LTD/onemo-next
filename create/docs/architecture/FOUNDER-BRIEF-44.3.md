## Part 1: What the Documentation Chain Says Right Now

### The Product (from Business + Product folders)

ONEMO is a fashion customization platform. The core product is the **Effect** — a modular, magnetically-attached piece that sits on a garment. Users upload artwork, configure it as an Effect, and buy a made-to-order premium product.

**Three product families at launch:**
1. **Effects** — Custom Standard (3 shapes), Custom Pair, Stock/Curated
2. **Garments** — Magnetic-grid T-shirt, Magnetic-grid Cap
3. **Bundles** — Effect + Garment starters

**Deferred but architecturally planned:** Shaped Effects, Hoodies, Velcro activation, Creator marketplace

**Three equal loops (non-negotiable):**
- Customization: upload → configure → review → buy
- Commerce: browse → evaluate → buy garments/stock Effects
- Social: save → share → discover → re-enter

**The physical constraint that drives everything:** Sublimation (heat printing) happens at 180-200°C. Magnets lose power at those temperatures. This single fact creates three manufacturing methods (A/B/C), all solving the heat-vs-magnets problem differently.

### What Create Must Do (from Requirements + UX Chain)

The Create PRD (3.3) defines 18 functional requirements (CREATE-FR-001 through CREATE-FR-018). In product language:

1. **Accept entry from anywhere** — catalog page, preset link, saved draft, or remix. Resolve valid product context before editing starts.
2. **Source-agnostic intake** — upload is first, but the pipeline must accept future sources (AI generation, connected imports) without rewriting.
3. **Anonymous start** — no account required to create and see a first preview.
4. **3D surface editing** — artwork positioned directly on the 3D product (replaces the old 2D canvas). Touch drag on the product surface.
5. **Precision assist** — numeric controls alongside gestures for exact placement (also the accessibility path).
6. **Gesture-to-canonical reconciliation** — what you drag on screen must produce deterministic coordinates for proof and manufacturing.
7. **Safe-area enforcement** — can't silently place artwork outside the printable zone.
8. **Variant configuration** — size, material, color, subtype, attachment system. Extends V1 with attachment awareness.
9. **Compatibility messaging** — when a configuration requires a garment, pair, or different product path, tell the user clearly.
10. **Back-side/attachment visualization** — show what the back looks like, how it attaches.
11. **Bundle suggestions** — suggest compatible garments/pairs. Advisory, not forced.
12. **Pair education** — explain how pairs work so users don't confuse pair vs single.
13. **Live preview with fallback** — if 3D can't load, degrade gracefully.
14. **Proof gate** — authoritative preview before buy. Uses canonical design state, not unsaved local state.
15. **Autosave + resume** — save on meaningful change, resume across sessions and account upgrades.
16. **Approved revision to Commerce** — hand off without mutating the design.
17. **Share/discovery seeding** — produce the metadata needed for public pages and remix.
18. **Mixed-cart support** — custom Effect + garments + stock items in one transaction path.

## Part 2: CTO Audit

### Red Flags

**1. The UX chain was generated, not designed.**
The 14-step chain was produced by Codex (GPT-5 Codex), upgraded by agents. It's academically rigorous (ISO 9241-210 traces, full traceability matrices) but reads like a specification machine, not a product designer. The artifacts are useful as structural scaffolding, but they should not be treated as gospel.

**2. CM-006 (Preview trust dossier) and CM-008 (Opportunity readiness frame) add complexity without clear product benefit.**
"Trust dossier" is academic language for "does the user believe the preview?" This can be a boolean flag on the review screen, not a separate domain object with its own lifecycle. "Readiness frame" models a time-sensitive purchase window — but our brand explicitly bans urgency tactics. These objects may be overengineering simple UI states.

**3. CM-012 (Authored outcome) and CM-013 (Identity set) are emotional constructs, not technical entities.**
"Authored outcome framing" asks: does the finished product feel personally authored? This is a UX quality measure, not a data object. Modeling it as a canonical Supabase entity with fields like `authored_verdict` and `meaning_summary` is overreach. Same for identity-set coherence — this is a post-MVP UI feature, not a day-one domain entity.

**4. The UX chain doesn't know about 3D.**
The V3 delta supplement had to patch in 3D surface gestures, precision assist, gesture reconciliation, safe-area awareness, and back-side visualization. None of these appeared in the original chain. This means the UX artifacts describe an interaction model that predates the core Create technology decision (3D configurator replaces 2D canvas).

**5. The operations folder isn't finished.**
The service blueprint is being consolidated. Returns policy research just came in. Shipping, fulfillment SLAs, and manufacturing operations are partially documented. Commerce architecture (Phase 5) depends on operations decisions that aren't locked yet.

### Unnecessary Complexity

**1. 14 content model objects is too many for MVP.**
MVP needs: ArtworkSource (CM-001), DraftRecord (CM-002), DesignWorkspaceState (CM-003), CommerceVariantContext (CM-004), and ActionSafetyEnvelope (CM-014). The rest are either derived (CM-005, CM-006, CM-008), deferred (CM-009, CM-010, CM-012, CM-013), or overlap with existing infrastructure (CM-007 overlaps with the revision snapshot concept, CM-011 maps to CheckoutIntent).

**2. The container model is correct but the vocabulary is heavy.**
Screens, shells, modes, overlays, states — 11 containers for Create. The routing (IA-01 through IA-05 + IA-11) is exactly right. The overlay and state containers (IA-09, IA-10) are valid concepts but they're implementation patterns, not product-level containers. They don't need domain objects.

**3. Known-good snapshot + live experiment pattern is premature.**
CM-003 has `known_good_snapshot_ref` and `live_experiment_summary` as first-class fields. This models "experiment with a change, compare to known-good, restore if unhappy." For MVP, undo/redo via revision history is simpler and covers the same user need.

### What's Missing

**1. No specification of the loading/bootstrap experience.**
What does the customer see when `/create` first loads? The UX chain describes IA-01 as an "intake screen" but doesn't specify what appears before the 3D scene is ready. This is a UX gap — the transition from landing to first interaction needs definition.

**2. Cap-specific and pair-specific 3D scenes are not designed.**
The delta supplement says caps need cap-specific geometry and pairs need pair visualization. But no scene presets, GLB models, or Studio workflows exist for caps or pairs. These are product gaps, not just architecture gaps.

**3. Bundle suggestion UI is unspecified.**
CREATE-FR-010 says suggest compatible garments/pairs. Where in the flow? How? The delta supplement says "in the review screen as secondary content" but the UX chain's IA-05 doesn't include bundle UI components.

**4. Attachment-system messaging consistency has no design spec.**
CREATE-FR-017 says keep messaging consistent across all views. But there's no message catalog or copy spec for attachment-system communication.

### What's Correct and Solid

- **The routing structure** (IA-01 through IA-05 + resume) is clean and correct
- **Source-agnostic intake** (CREATE-FR-002) is well-defined
- **The proof gate** (CREATE-FR-012, FEAT-04) is the right boundary
- **Commerce separation** — Shopify never owns design truth. CheckoutIntent/CM-011 correctly models the handoff.
- **The product system** as a canonical graph that every module references — correct and essential.
- **Autosave + resume + anonymous continuity** — well-specified across multiple documents.
- **The four canonical artifacts** (ProductSpec, ScenePreset, DesignSession, ManufacturingPackage) — correct, stable.
