## KAI-4781 — Orbit Drift Fix

**Verdict: PASS**

### Change 1: CameraConfigSync — setTimeout cascade removed

**Before:** Camera config was applied once, then re-applied via 4 `setTimeout` calls at 0ms, 50ms, 150ms, 500ms. Each timer re-ran the full camera + controls update, creating a race window where OrbitControls damping updates and user input could interleave with the retries.

**After:** Camera config applied once, synchronously. No timers. No cleanup function needed.

**Why this is correct:**
- The `useEffect` runs after React commit, at which point the R3F canvas and OrbitControls are fully mounted. The original timers were a workaround for R3F initialization timing — but `CameraConfigSync` already receives the live `camera` from `useThree`, which only resolves after the Canvas is committed. The timers were redundant.
- The signature-based dedup (`appliedSignatureRef`) prevents re-application on re-renders where config hasn't changed. This is preserved.
- The `else` branch (`camera.lookAt(...)` when no controls) is now properly reachable — previously the early `return` inside the controls block was inside the nested `applyCameraConfig` function, but the semantic was the same.

### Change 2: OrbitControls `target` prop removed

**Before:** `<OrbitControls target={cam?.target ?? [0, 0, 0]} ... />`

**After:** `<OrbitControls makeDefault enableDamping={...} ... />` — no `target` prop.

**Why this is correct:**
- When `target` was passed as a prop, drei's OrbitControls would reset the orbit target on every re-render where `cam.target` changed — competing with `CameraConfigSync` which also sets `controls.target.set(...)` imperatively. This created a double-write: React prop sets target → CameraConfigSync sets target again → damping interpolates between them → drift.
- With the prop removed, `CameraConfigSync` is the single writer to `controls.target`. The `OrbitControlsOverride` in StudioViewport also writes to `controls.target` (orbit reset, scene camera switch), but those are user-initiated actions, not competing re-renders.
- Initial target is set by `CameraConfigSync` on first run (when signature changes from `null` to the config signature). No gap where target is unset — `OrbitControls` defaults to `(0, 0, 0)` before `CameraConfigSync` fires, which matches `cam?.target ?? [0, 0, 0]`.

### Drift risk areas (from pre-read) — all addressed

| Risk | Status |
|------|--------|
| setTimeout race with damping | Eliminated — timers removed |
| Dual target writers (prop + imperative) | Eliminated — prop removed |
| `enableDamping` without frame-loop `update()` | Not affected by this change — drei's `makeDefault` OrbitControls hooks into R3F's frame loop automatically |
| Multiple imperative target mutations (OrbitControlsOverride, CameraCommandController, etc.) | These are user-action-driven, not competing re-render-driven. No conflict. |
