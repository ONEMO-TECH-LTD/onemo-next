## KAI-4782 — Orbit Center Reset

**Verdict: PASS**

This fix is the same underlying change as KAI-4781 (orbit drift) from Batch 2 — removing the `target` prop from OrbitControls in EffectViewer.tsx.

### Why this fixes orbit center reset
The `OrbitControlsOverride.resetOrbitCenter()` function (lines 1916-1940) sets `controls.target` imperatively to the selected object's world position or the scene bounding box center. Previously, the `<OrbitControls target={cam?.target ?? [0,0,0]} />` prop would overwrite this on the next React re-render, snapping the orbit center back to the config target. With the prop removed, `resetOrbitCenter`'s imperative writes persist correctly.

Same fix, different symptom:
- KAI-4781: orbit drift during damping (prop competing with CameraConfigSync)
- KAI-4782: orbit center reset not sticking (prop overwriting resetOrbitCenter)

No additional code changes were needed — already fixed by the Batch 2 target prop removal.

## KAI-4786 — Camera Clear Color Scoping

**Verdict: PASS**

### Change 1: ActiveCameraRuntimeSync — clear color moved outside signature guard

**Before:** Clear color was applied inside `if (signature !== signatureRef.current)`, meaning it only ran when camera userData changed. Once the signature stabilized, clear color was never re-applied — if another render pass (e.g., the preview renderer) changed `gl.clearColor`, it would persist into the next frame's main render.

**After:** Clear color is applied every frame via `useFrame`, outside the signature-gated block (lines 1235-1249). The toneMapping and colorSpace settings remain inside the signature guard (they're expensive to set and don't get overwritten by other render passes).

**Why this is correct:**
- `useFrame` runs before every render (priority 0 = default = before render)
- Clear color is cheap to set — just a color + alpha on the WebGLRenderer
- The pattern is: set clear color → main render happens → preview renderer (priority 1) may change clear color → next frame's `useFrame` restores it
- The `else` branch (`gl.setClearColor(config.colors.bgColor, 1)`) ensures the scene background is always the baseline when no camera-specific clear color is set

### Change 2: SceneCameraPreviewRenderer — save/restore clear color

**Before:** Preview renderer set scissor test and viewport but did not touch clear color. If a preview camera had `userData.clearColor`, it was ignored. If the main camera had changed clear color, the preview would inherit it.

**After (lines 1522-1543):**
1. Save previous clear color: `gl.getClearColor(new THREE.Color())` + `gl.getClearAlpha()`
2. Check preview camera's `userData.clearColor` — apply if present
3. Render the preview
4. Restore previous clear color: `gl.setClearColor(prevClearColor, prevClearAlpha)`

**Why this is correct:**
- `getClearColor(target)` returns the current clear color into the provided Color object — correct Three.js API usage
- The null check on `camClearColor` means the preview only overrides clear color if the camera entity has one configured. Otherwise it inherits the main camera's clear color (which is correct — preview should show what the camera would see)
- Restore runs after `gl.render()`, before returning control. The priority 1 ensures this runs after the main render

### Frame sequence verification

| Step | Priority | What happens |
|------|----------|-------------|
| 1 | `useFrame` p0 | `ActiveCameraRuntimeSync` sets main camera clear color |
| 2 | R3F render | Main scene renders with correct clear color |
| 3 | `useFrame` p1 | `SceneCameraPreviewRenderer` saves clear color, applies preview camera's color, renders preview, restores clear color |
| 4 | Next frame p0 | `ActiveCameraRuntimeSync` re-applies main camera clear color |

No clear color leaks between passes. No frame where the wrong color persists.

### Edge case: no preview camera active

When no preview camera is rendered, `SceneCameraPreviewRenderer` doesn't run. `ActiveCameraRuntimeSync` still sets clear color every frame. No issue.

### Edge case: clear color array validation

Both `ActiveCameraRuntimeSync` (line 1189) and `SceneCameraPreviewRenderer` (line 1527) use the same validation pattern:
```ts
Array.isArray(camera.userData?.clearColor) && camera.userData.clearColor.length >= 3
```
Consistent. Falls back to `null` if missing or malformed. `Number(... ?? 1)` provides safe defaults for each channel.
