## FINDINGS

### A — MEDIUM (design fidelity, headline): multi-axis wire mis-anchoring + frame-crossing
On any component **with variant axes**, there is **no un-grouped base frame** on the board — every config frame (`size=sm/lg`, `tone=a/b`) sits inside a `[data-axis-group]`; only state ghosts are un-grouped. `NodeLayer.baseFrame()` selects `no-state && not-in-axis-group` → **finds nothing** → falls back to `querySelector('[data-component-frame]')` = the **first frame (`size=sm`)**. Consequence, measured + screenshot-confirmed:
- The **state (hover) connector — a COMPONENT-GLOBAL base transition** — draws its wire from **`size=sm`'s bottom**, straight down **through the unrelated `tone=a` frame** (the ⚡ badge overlaps `tone=a`'s content), to the `hover` ghost. It reads as *"`size=sm` (and `tone=a`) own the hover transition"* — false; the transition is component-global.
- Framer anchors the wire to the true base/source variant with the state variant **adjacent below** (short, crosses nothing). Here the axis-grouped layout puts 2 axis rows between the mis-picked source and the state ghost, so the wire is long and crosses frames.
- **This is the flagship visual, and it looks broken on the common case** (most real components have ≥1 axis).
- **Fix:** give the wire layer a real base/source anchor for an axis'd board — e.g. anchor component-global (state) wires to the component group's origin/header rather than an arbitrary axis-value frame, and route wires to avoid crossing unrelated frames (or render a dedicated base/default frame to anchor from). **Cost:** moderate (rework `baseFrame` resolution + wire routing). **Recommend:** pre-merge or fast-follow — not ship-as-is for Dan.

### B — LOW (fidelity): missing ▶ play badge on state variants
Framer marks state/interaction variants with a purple **▶ play badge** on the frame label (extraction doc §lifecycle; build item 5 "align labels"). **Not cloned** — measured `playBadge=false`; state ghost frames carry no ▶. **Fix:** add the ▶ marker to state-ghost frame labels. **Cost:** trivial. **Recommend:** fast-follow deslop.

### C — LOW/MED (redundancy / deslop): two authoring paths for the same connector
The old I4 side-panel "Connectors" buttons remain (`page.tsx:4070`, comment literally *"minimal connector-authoring trigger"*) **alongside** the new canonical wire layer. Two ways to author the same `set-connector` = redundant cognitive load + "which is canonical?" ambiguity. My independent read: the I4 side-panel was always scaffold ("minimal trigger now, the board replaces it"); now that the wire layer ships it should be **removed** so the wire is the single authoring surface — matches Framer (one path) and the restructure-removes-old-surface discipline. **Fix:** delete the I4 Connectors section. **Cost:** small. **Recommend:** deslop. *(Reached independently; the target is unambiguous given the I4 "minimal trigger → board replaces it" history.)*

### D — LOW (interaction fidelity): drag-handles on every frame, but the source frame is ignored
A diamond handle renders on **every** frame's edge, but the committed connector is built purely from the **drop target** — the source frame the drag started from is never referenced (connectors are component-level). So dragging from `tone=b`'s handle to a target writes the same base-anchored connector as dragging from anywhere. The multi-frame handles imply a per-frame **source→target** semantic the engine doesn't have; and the drag rubber-band starts at the handle but the committed wire re-anchors to the (mis-picked) base — the wire visibly **jumps origin** after drop. **Fix:** either show ONE handle on the base/source only, or make the committed wire anchor match the drag origin. **Cost:** small–moderate. **Recommend:** fold into Finding A's base-anchor rework.

**Design judgment on elbow-routing (my call): reads as a workaround, not Framer-like.** Framer uses short straight wires between co-located variants; this loops every wire across the full board width to a single far-right gutter and back, wires overlap in the gutter, and the return still crosses the target row. **Recommendation:** don't route all wires through one fixed far-right gutter. Either (a) enter each target from its **nearest clear edge / shortest orthogonal clear path** (so a leftmost target is approached from the left, crossing nothing), or (b) the more Framer-faithful fix — reconsider the board layout so connector targets sit adjacent to their source. Part-1 base-frame fix is good and can stay.

# CLOSURE RE-VERIFY #2 — fix `d7898ca` (corridor+channel routing)

**Method:** rebuilt the exact multi-axis probe on `d7898ca`; measured BOTH wire paths' segments against ALL 9 frame rects (not just the previously-flagged one) + the channel clearance. Worktree clean after.

**VERDICT: Finding A Part-2 — CLOSED ✓** (with one LOW robustness nit).

- **Zero crossings, both wires, all 9 frames — measured.** `state:hover` crossed=[], `switch:size` crossed=[]. The routing (`src exit on nearest side → margin corridor → channel at `tr.top-12` above the target row → drop into target TOP edge`) provably clears every frame on the exact repro. Screenshot: the hover wire drops the left-margin corridor and enters hover from the top; the switch wire takes a short top-approach to size=lg — nearest-side keeps them short (no full-width loop).
- **Design read (my call): reads CLEAN and intentional now — no longer a workaround.** It's not Framer's straight-line aesthetic (Framer co-locates a variant with its states so straight wires suffice), but given OUR axis-grouped layout genuinely separates base from the wide states row, orthogonal Manhattan routing that provably avoids crossings is a legitimate, professional node-editor convention. Accept.

**LOW nit — the fixed 12px channel offset is coupled to the board's flex gap.** `channelY = tr.top - 12`; the channel stays clear only while the inter-row gap > 12px. Measured here: gap 33px → 21px clearance (fine). But the board's *minimum* flex gap is 16px, so the tightest current layout leaves only ~4px clearance, and a hardcoded 12px silently breaks (channel lands inside the frame above → crossings return) if any denser layout / compact mode / CSS change drops the gap below 12px. **Real fragility, not a current break.** Recommend: derive `channelY` from the *measured* gap (midpoint of `frameAbove.bottom → target.top`) instead of a fixed 12px — adapts to any spacing, always centers in the clear band. Small change; the lead's density concern is legitimate.
